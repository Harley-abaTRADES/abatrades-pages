1. Purpose

This document is the technical specification for automating aba TRADES membership email communication. It describes the exact stack, the data flow, the credentials, the note-log write-back format, and the cohort logic, and it records clearly which parts are proven working versus pending live go. It exists so any future operator - human or AI - can read it and reconstruct, operate, or extend the system without rediscovering the hard-won details.

Status: built and unarmed (29 Sep 2026)
This is a living document. It captures the verified state as of 29 Sep 2026. Schedule: the scheduler (Option 2) replaces the n8n Wait-journey that was abandoned because this n8n instance cannot activate Wait-node workflows (300-scope check failed: "object is not iterable"). Brevo contact attributes are now the source of truth for member progress; a daily scheduler cron drives the sends. Flows are built and UNARMED - no real member is in the flow (no MEMBER_FLOW_ACTIVE=true on any real contact) until the staged test passes and go-live is signed. The earlier SOP 001 covers SMS campaigns.

2. Scope

In scope:

  • The membership evergreen email journey (new-member flow) and the member invoice-paid trigger flow.
  • The daily scheduler (cron + bin/member_flow_scheduler.py) as the journey engine, with Brevo contact attributes as the source of truth for each member's stage.
  • Brevo as the transactional email sender (per-member, template-based).
  • The ServiceTitan Customer Note write-back so the CSR team sees what was sent to each customer.
  • Treatment/control cohort assignment and the measurement baseline.

Out of scope for this SOP (see future revisions):

  • The commercial rationale and customer-lifetime-value analysis behind membership (covered in the CLV deck, not here).
  • Marketing-pro campaign management in ServiceTitan (covered separately; the API cannot build those).
  • SMS sending (future: same note-log format with a channel emoji; not yet built).
  • Direct-mail / traditional channel automation.

Brevo's transactional /smtp/email API does NOT auto-suppress against the blacklist the way marketing campaigns do. So sending transactionally means WE must maintain suppression. That is cron 2 exactly: it polls Brevo's opt-out/blacklist and PATCHes the ServiceTitan contact's preferences.marketingUpdatesEnabled=false (ST is the source of truth for consent; the send audience must read consent from ST). The blacklist MUST be read from /smtp/blockedContacts (the authoritative surface) UNION /contacts where emailBlacklisted=true - reading only /contacts silently misses the flag shape and under-counts. Join key: Brevo contact attribute ST_CUSTOMER_ID, written by cron 1, so contacts without it are skipped for manual review. Cron 2 must be verified running before any live send.

3.2 Core architecture decision (revised 29 Sep 2026)

Use a daily scheduler (bin/member_flow_scheduler.py under a Hermes cron) as the journey engine, with Brevo contact attributes as the single source of truth for each member's position in the series. The scheduler reads each member's stage attributes each day, sends the email whose date has arrived (Brevo transactional per-member, templateId - not marketing-campaign objects), writes the 📧 Member Flow E# ST note, and advances the attributes. Analytics are pulled from Brevo statistics.

Why the scheduler (and not n8n Wait): this self-hosted n8n instance cannot activate any workflow containing a Wait node (proven 29 Sep with a minimal webhook-to-Wait probe - n8n returns "object is not iterable" because held/paused executions are not enabled on the instance; enabling them would require queue mode + Redis + a worker, a whole-instance infra change). The scheduler needs no n8n change, holds no in-flight execution (a 90/390-day email is just a date the cron compares), and survives restarts - the state lives in Brevo, not in a process.

Why Brevo transactional, not marketing-campaign
Per-member evergreen timing is incompatible with marketing-campaign objects (a campaign is a batch blast; per-member timing would need a campaign per send). Transactional per-member sends are the fit. Marketing campaigns stay for genuine batch blasts.

3.3 The logic: how the scheduler decides what to send

  • Only contacts with MEMBER_FLOW_ACTIVE=true and an opted-in email are considered (the arming gate - no real member has this set until go-live).
  • The scheduler holds per-member state on the Brevo contact, not in-world (see section 5.3).
  • Each day it sends at most ONE email per member (whichever is first due), so a run is deterministic and never batches.
  • Rotation/trade logic is computed from the member's SERVICE_TYPE at run time (E2 entrance + which 3 opener articles appear neutralised), so no n8n branch/switch nodes are needed.

5.1 Scheduler - join track (Welcome + the two time-bound emails)

A member enters when MEMBER_FLOW_ACTIVE=true. On the first run for that contact the scheduler sends E1 Welcome (Final Series E1, id 30) to every member, no cohort filter, writes the 📧 Member Flow E1 ST note, and sets CLOSE_AT (+90 days) and RENEW_AT (+390 days). Later daily runs fire E12 Close (id 45) when CLOSE_AT arrives and E14 Renewal (id 47) when RENEW_AT arrives, each with its own note.

5.2 Scheduler - billing track (E2 entrance + rotation)

When MEMBER_BILLED_AT is set (billing sync), the scheduler sends E2 First cross-trade (trade-specific entrance, ids 31-34) at the billed date - the opener references the trade just used - then one rotation email every ~3 weeks: E3 Switchboard, E4 Tap fix, E5 AC filter, E6 Roof leaks, E8-E11 (the three non-entrance opener articles in neutralised form + Adelaide water), then E13 Renovation (id 46). The sequence is computed from the member's SERVICE_TYPE at run time; which three opener articles appear neutralised depends on the entrance trade. MEMBER_ROT_POS (0-9) tracks how many billing-track emails have been sent.

6. ServiceTitan note-log write-back (CSR visibility)

Decision (Josh 24 Sep 2026): every email (and eventually SMS) sent to a member is logged as a ServiceTitan Customer Note on the customer record, so the CSR team can see what was sent, to whom, and when. ST has no per-contact email-history write via API, so the note lives at the customer level.

6.1 Endpoint

1. Create a note: POST /crm/v2/tenant/3306271893/customers/{customerId}/notes with body { "text": "..." }. Uses the write key.
2. Read back / verify: GET /crm/v2/tenant/3306271893/customers/{customerId}/notes.

6.2 Note format (locked 24 Sep 2026, rev 4 — prefixed "Member Flow")

ST auto-appends the Created date/timestamp under each note, so the note text does NOT include a timestamp (avoids double handling). The template copy already ends with the email's own signature footer, so the note does NOT append a second signature either. Format:

📧 Member Flow E1 · Welcome · template #1 · harley@abatrades.com.au
Subject: You're in! 🎉 Welcome to aba TRADES membership
(blank line)
[full plain-text copy, HTML stripped - ends with the template's own Harley / aba TRADES Support Team / 45 Henry St footer]
  • First line: channel emoji (📧 email / 📱 SMS later) · Member Flow · journey step + name · template #N · from address.
  • Then the Subject line verbatim, then the full word-for-word plain-text body.
  • No appended signature line (the template footer is already part of the copy - appending one creates a duplicate footer). No recipient, no timestamp.
  • SMS later reuses the same shape with 📱.

6.3 Verified facts behind the format

7. Cohort logic (treatment vs control)

7.1 How assignment works

1. At member_joined time, the flow resolves each member deterministically: a hash of the ServiceTitan customer ID maps to COHORT = treatment or control.
2. The cohort is written into Brevo as a contact attribute (COHORT). Brevo is the source of truth for which arm a member is in.
3. E1 (welcome) goes to EVERY member, no cohort filter. The gate applies only from E2 onward (nurture sends filter COHORT = treatment; control receives nothing during the measurement window).

7.2 Measurement

  • Baseline: 1,223 sendable members (email + consent + not doNotMail).
  • Split: 75/25 (Josh-confirmed 24 Sep 2026) = ~917 treatment / ~306 control.
  • All cohort attributes are assigned deterministically (logic-based, foolproof), never AI-judged.
  • Control must receive nothing during the measurement window - do not contaminate the read.
Not yet live
The cohort-writing step (cron 1 lane A) is currently PAUSED, so no COHORT values exist in Brevo yet. It is armed only when the journey goes live.

To stop the page growing unbounded, the group landing is tabulated within itself into Leads / Revenue / Email. The Email area is itself split into three sub-tabs: Flows, Campaigns, and a temporary A/B Test. The A/B Test tab lasts exactly the duration of the trial and then is removed from the dashboard. Rows that would overlap between the A/B Test and Flows (sends/opens/clicks for the trial cohort) stay on Flows; the A/B tab carries only the uplift outcome that the A/B read can provide.

8.2 Attribution stitching - jobs and revenue back to the email channel

The strongest stitch already exists for free. Because every send writes a ServiceTitan Customer Note to the customer record (section 6), we already know exactly which members received which email, identified by customerId. The member phone line and email replies are not needed to establish who is in the funnel. This gives two layers, and they must not be conflated:

  • Layer 1 - recipient exposure attribution (deterministic). Join the recipient set (from ST notes, by customerId) to jpm/v2/jobs (by customerId) for booked jobs and accounting/v2/invoices (by customerId) for revenue. This yields per-flow jobs and revenue. It is exposure-attributed, never claim it as "caused by email".
  • Layer 2 - causation (the A/B uplift). Because control members also book and spend without any emails, only the treatment-vs-control delta removes the would-have-booked-anyway baseline. Present the delta as the causal read; present the raw per-channel numbers as exposure only.

8.3 The phone number and email-reply pathways

  • Unique member phone number: Assumption (Josh 24 Sep 2026, validation pending) - the member inbound line is widened to ServiceTitan call tracking and automatically maps the campaign type as "trades and membership". If confirmed, inbound calls + bookings from that number carry a membership/trades campaignId, so the campaign reports (1314 InboundCalls, 1386 TotalJobsBooked/CompletedRevenue) and the group's existing leadsByCampaign machinery pick them up as a membership campaign (the campaignTypes pattern derives type Membership from a "TRADES - Membership" name). This is channel-level attribution (anyone who calls the line), not per-recipient, and it complements the recipient-exposure layer. Validation gate before relying on it: confirm the member number is actually campaign-tracked in ST and which campaign it maps to.
  • Email replies: land in a shared mailbox with no native ServiceTitan link, so they are not a reliable stitch unless a reply-to-booking capture flow is built. Not planned; skip for attribution.
Revenue measure + double-count rule
Revenue measure: per-member via invoice total (GST-inclusive, good for relative uplift / AOV, labelled non-reconciling). Report 295 is per-business-unit, not per-customer, so it is not the tool for member-level attribution. Double-count rule: a member's booked job may also carry a marketing campaignId (Google Ads / SMS) via the manual Campaign field on the ticket. Counting it under both "membership" and another channel double-counts the group roll-up (violates the no-double-count rule). Rule: a job carrying a named marketing campaignId is attributed to that channel; the membership channel row counts jobs not otherwise campaign-tagged (membership as fallback/touch attribution). This precedence is an open decision for Josh/Paul before the feed is wired.

8.4 Data sources and feed wiring

  • Sends: ST notes (count the 📧 Member Flow E1 · ... template #N prefix per step per day) today, cross-checked against Brevo.
  • Opens / clicks / delivered / bounced: Brevo /smtp/statistics/report (aggregate) plus per-step once each send carries a step/template/cohort tag (a small n8n send-payload change, queued - not built as part of this design).
  • Jobs + revenue: ST jpm/v2/jobs + accounting/v2/invoices by customerId over the recipient set.
  • Cohort: Brevo COHORT attribute joined to ST_CUSTOMER_ID.
  • Feed: add a group.email section to gen_group_feed.py + CONTRACT.schema.json; the member pull is a new source module following the standard add-a-channel pattern (contract always carries the section, zeroed on failure).

9. Verification gates and the "never claim success without evidence" rule

  • A webhook 200 is an acknowledgement, not a delivery. "Workflow was started" only means the trigger ran.
  • Confirm what actually ran from the SQLite DB (read-only): execution_entity (status/finished) and execution_data (runData = which nodes ran, lastNodeExecuted). If runData contains ONLY the trigger, the chain did not advance - investigate, do not assume a delivery.
  • Confirm Brevo delivery via GET /smtp/statistics/events?email=<recipient> returning an event: delivered. The messageId from a POST 200 is acceptance, not delivery.
  • Confirm ST note-write via read-back of the customer's notes, and on-screen by the CSR.
Human-in-the-loop gate for writes from chat
Any DELETE / PATCH / PUT issued from a chat session (troubleshooting, or any request to do so) must be flagged and paused for explicit Tier-4 approval first, even for a single record - state the object, id, scope and blast radius. Scripted flows already approved to run autonomously (the journey flow's sends + note-write, the consent write-back) do NOT need a per-action go.

10. Learnings and pitfalls (append as discovered)

  • (24 Sep 2026) n8n routes connections by node name, not id. An authoring helper writing ids into the connections map leaves dangling edges: the trigger fires, nothing downstream runs, recorded as success. Fix: key both the connection-map source and every edge target by the node's display name.
  • (24 Sep 2026) httpRequest custom headers must go via sendHeaders + headerParameters, NOT options.headers - HttpRequest V3 drops options.headers for auth headers (silent 401).
  • (24 Sep 2026) ST rejects a scope param on its token endpoint (EAUTH); leave the OAuth2 credential scope empty - ST derives scopes from the app grant.
  • (24 Sep 2026) A n8n-nodes-base.httpRequest node ignores an attached credential unless authentication: genericCredentialType + the auth type param are set. Without it, no auth header is sent (Brevo 401 "authentication not found in headers").
  • (23-24 Sep 2026) Pin n8n 1.122.4. 1.120.0 crashes at startup (#22440). npm install is slow on this single-core box - run it backgrounded with a notify.
  • (24 Sep 2026) Switch node: match the parameter shape to its typeVersion. V1 reads mode/dataType/value1/rules[].output/fallbackOutput; V2/V3 differ. V1 positional outputs map 1:1 to connections[].main[i].
  • (24 Sep 2026) Webhook data nests under $json.body. A POST/JSON webhook exposes payload at $json.body.<field>, not $json.<field>.
  • (24 Sep 2026) ST note-write can return 200 with a note id yet the note not appear immediately in read-back - eventual consistency; re-check before concluding.
  • (2026) Long installs / feed regens must run backgrounded (exit-124 on foreground timeout), and a partial global install gets npm uninstall -g before reinstall.
