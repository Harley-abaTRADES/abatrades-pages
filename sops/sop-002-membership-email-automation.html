1. Purpose

This document is the technical specification for automating aba TRADES membership email communication. It describes the exact stack, the data flow, the credentials, the note-log write-back format, and the cohort logic, and it records clearly which parts are proven working versus pending live go. It exists so any future operator - human or AI - can read it and reconstruct, operate, or extend the system without rediscovering the hard-won details.

Status: build-in-progress
This is a living document. It captures the verified state as of 24 Sep 2026. Once the flow is live, revisit and correct anything that has drifted. The earlier SOP 001 covers SMS campaigns; this covers the membership email journey.

2. Scope

In scope:

  • The membership evergreen email journey (new-member flow) and the member invoice-paid trigger flow.
  • The self-hosted n8n instance as the journey engine (API-authored, versioned JSON flows).
  • Brevo as the transactional email sender (per-member, template-based).
  • The ServiceTitan Customer Note write-back so the CSR team sees what was sent to each customer.
  • Treatment/control cohort assignment and the measurement baseline.

Out of scope for this SOP (see future revisions):

  • The commercial rationale and customer-lifetime-value analysis behind membership (covered in the CLV deck, not here).
  • Marketing-pro campaign management in ServiceTitan (covered separately; the API cannot build those).
  • SMS sending (future: same note-log format with a channel emoji; not yet built).
  • Direct-mail / traditional channel automation.

3. Source of truth and architecture

3.1 Systems in the stack

SystemRoleKey detail
n8n (self-hosted)Journey / orchestration engineAPI-authored JSON flows on the box at $0 software. Runs every flow.
Brevo (ESP)Transactional email senderPer-member sends via template ID. Source of truth for delivery/open/click.
ServiceTitan (CRM)System of record + consent + note-logCustomer/contact records; the Customer Note is where sent-emails land for the CSR team.
Self-hosted cronsDeterministic syncCron 1 (members in), cron 2 (unsubscribes out) - logic-based, foolproof. Cron 2 restored + hardened 24 Sep (id 1a18497752df, every 6h).
Transactional sends bypass Brevo's opt-out list - suppression is OURS to own
Brevo's transactional /smtp/email API does NOT auto-suppress against the blacklist the way marketing campaigns do. So sending transactionally means WE must maintain suppression. That is cron 2 exactly: it polls Brevo's opt-out/blacklist and PATCHes the ServiceTitan contact's preferences.marketingUpdatesEnabled=false (ST is the source of truth for consent; the send audience must read consent from ST). The blacklist MUST be read from /smtp/blockedContacts (the authoritative surface) UNION /contacts where emailBlacklisted=true - reading only /contacts silently misses the flag shape and under-counts. Join key: Brevo contact attribute ST_CUSTOMER_ID, written by cron 1, so contacts without it are skipped for manual review. Cron 2 must be verified running before any live send.

3.2 Core architecture decision (Josh-signed 23 Sep 2026)

Use self-hosted n8n as the journey engine (API-authored, versioned, AI-editable JSON flows) with Brevo transactional sends (per-member, templateId - not marketing-campaign objects) and analytics pulled programmatically from Brevo statistics. Suppression on the transactional path is owned by us deterministically (cron 2 + unsubscribe tag in templates).

Why Brevo transactional, not marketing-campaign
Per-member evergreen timing is incompatible with marketing-campaign objects (a campaign is a batch blast; per-member timing would need a campaign per send). Transactional per-member sends are the fit. Marketing campaigns stay for genuine batch blasts.

3.3 Why n8n and not the Brevo canvas

  • Brevo's canvas has no authoring API; n8n workflows are JSON we create/edit/pivot via API.
  • n8n Switch node does an N-way branch in one node; Brevo's canvas is 2-way-split limited.
  • Self-hosted = $0 software, reuses box you already pay for.

4.3 ServiceTitan API notes

  • Tenant: 3306271893. Base: https://api.servicetitan.io/{module}/v2/tenant/{tenant}/... (reporting uses reporting/v2/tenant/{tenant}/.../).
  • OAuth2 client-credentials token (15-min expiry, no refresh). Every call needs BOTH Authorization: Bearer <token> AND ST-App-Key header.
  • Rate limit ~60 req/s; reporting module far stricter (~1/min per report). Send a browser-like User-Agent.

5. The flows (process map)

5.1 Flow A - member_joined evergreen journey (the main flow)

Trigger: a member joins. n8n webhook receives the event, branches by service type, and produces the day-0/7/21/45/90 sequence via Brevo transactional sends, with a ServiceTitan note-log on each send.

1. Trigger (webhook): member_journey receives { customerId, service_type, member_joined_date, first_name }.
2. Switch: n8n-nodes-base.switch (version 1, positional outputs) branches on service_type to Aircon / Plumbing / Electrical / Roofing. Fallback output catches unknowns.
3. Day 0 send: Brevo transactional POST /smtp/email with the E1 Welcome template (id 1) to all members (no cohort filter).
4. Days 7/21/45: cross-trade value emails (templates 2-13) - only to the treatment cohort, branch-specific.
5. Day 90: hard close on the free annual inspection (templates 14/15).
6. After every send: write the note to ServiceTitan (see section 6).
Sequence timing
The flow matches the real re-engagement rhythm (median ~200 days between fresh jobs). A 14-day flow is a trap - don't trim to it. The 90-day span is deliberate so the last email lands near the measurement read.

5.2 Flow B - member_invoice_paid trigger

1. Trigger (webhook): member_paid receives { customerId, service_type, paid_date }.
2. Switch: branch on service_type to the relevant E2 cross-trade send.
3. Send + note: Brevo send then ServiceTitan note-log, same as Flow A.

6. ServiceTitan note-log write-back (CSR visibility)

Decision (Josh 24 Sep 2026): every email (and eventually SMS) sent to a member is logged as a ServiceTitan Customer Note on the customer record, so the CSR team can see what was sent, to whom, and when. ST has no per-contact email-history write via API, so the note lives at the customer level.

6.1 Endpoint

1. Create a note: POST /crm/v2/tenant/3306271893/customers/{customerId}/notes with body { "text": "..." }. Uses the write key.
2. Read back / verify: GET /crm/v2/tenant/3306271893/customers/{customerId}/notes.

6.2 Note format (locked 24 Sep 2026, rev 2)

ST auto-appends the Created date/timestamp under each note, so the note text does NOT include a timestamp (avoids double handling). Format:

📧 E1 · Welcome · template #1 · harley@abatrades.com.au
Subject: You're in! 🎉 Welcome to aba TRADES membership
(blank line)
[full plain-text copy, HTML stripped]
(blank line)
— Harley · aba TRADES Support Team
45 Henry St, Stepney SA 5069 · www.abatrades.com.au
  • First line: channel emoji (📧 email / 📱 SMS later) · journey step + name · template #N · from address.
  • Then the Subject line verbatim, then the full word-for-word plain-text body.
  • No recipient (it is on the customer record). No timestamp (ST adds it).
  • SMS later reuses the same shape with 📱.

7. Cohort logic (treatment vs control)

7.1 How assignment works

1. At member_joined time, the flow resolves each member deterministically: a hash of the ServiceTitan customer ID maps to COHORT = treatment or control.
2. The cohort is written into Brevo as a contact attribute (COHORT). Brevo is the source of truth for which arm a member is in.
3. E1 (welcome) goes to EVERY member, no cohort filter. The gate applies only from E2 onward (nurture sends filter COHORT = treatment; control receives nothing during the measurement window).

7.2 Measurement

  • Baseline: 1,223 sendable members (email + consent + not doNotMail).
  • Split: 75/25 (Josh-confirmed 24 Sep 2026) = ~917 treatment / ~306 control.
  • All cohort attributes are assigned deterministically (logic-based, foolproof), never AI-judged.
  • Control must receive nothing during the measurement window - do not contaminate the read.
Not yet live
The cohort-writing step (cron 1 lane A) is currently PAUSED, so no COHORT values exist in Brevo yet. It is armed only when the journey goes live.

8. Verification gates and the "never claim success without evidence" rule

  • A webhook 200 is an acknowledgement, not a delivery. "Workflow was started" only means the trigger ran.
  • Confirm what actually ran from the SQLite DB (read-only): execution_entity (status/finished) and execution_data (runData = which nodes ran, lastNodeExecuted). If runData contains ONLY the trigger, the chain did not advance - investigate, do not assume a delivery.
  • Confirm Brevo delivery via GET /smtp/statistics/events?email=<recipient> returning an event: delivered. The messageId from a POST 200 is acceptance, not delivery.
  • Confirm ST note-write via read-back of the customer's notes, and on-screen by the CSR.
Human-in-the-loop gate for writes from chat
Any DELETE / PATCH / PUT issued from a chat session (troubleshooting, or any request to do so) must be flagged and paused for explicit Tier-4 approval first, even for a single record - state the object, id, scope and blast radius. Scripted flows already approved to run autonomously (the journey flow's sends + note-write, the consent write-back) do NOT need a per-action go.

9. Learnings and pitfalls (append as discovered)

  • (24 Sep 2026) n8n routes connections by node name, not id. An authoring helper writing ids into the connections map leaves dangling edges: the trigger fires, nothing downstream runs, recorded as success. Fix: key both the connection-map source and every edge target by the node's display name.
  • (24 Sep 2026) httpRequest custom headers must go via sendHeaders + headerParameters, NOT options.headers - HttpRequest V3 drops options.headers for auth headers (silent 401).
  • (24 Sep 2026) ST rejects a scope param on its token endpoint (EAUTH); leave the OAuth2 credential scope empty - ST derives scopes from the app grant.
  • (24 Sep 2026) A n8n-nodes-base.httpRequest node ignores an attached credential unless authentication: genericCredentialType + the auth type param are set. Without it, no auth header is sent (Brevo 401 "authentication not found in headers").
  • (23-24 Sep 2026) Pin n8n 1.122.4. 1.120.0 crashes at startup (#22440). npm install is slow on this single-core box - run it backgrounded with a notify.
  • (24 Sep 2026) Switch node: match the parameter shape to its typeVersion. V1 reads mode/dataType/value1/rules[].output/fallbackOutput; V2/V3 differ. V1 positional outputs map 1:1 to connections[].main[i].
  • (24 Sep 2026) Webhook data nests under $json.body. A POST/JSON webhook exposes payload at $json.body.<field>, not $json.<field>.
  • (24 Sep 2026) ST note-write can return 200 with a note id yet the note not appear immediately in read-back - eventual consistency; re-check before concluding.
  • (2026) Long installs / feed regens must run backgrounded (exit-124 on foreground timeout), and a partial global install gets npm uninstall -g before reinstall.
