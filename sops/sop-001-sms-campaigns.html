SOP 001 - SMS Campaigns

How to identify, validate and export the SMS campaign audience from ServiceTitan. This is a living document: procedure, learnings and pitfalls are appended as campaigns ship.

1. Purpose

Define the repeatable, cross-checked way to pull the audience for an SMS campaign out of ServiceTitan: who is a current member, which business units those members sit in, and what job types they have had. The same numbers must be reproducible by anyone at any time, and every headline figure carries a two-way validation so the team can trust the count before a send.

2. Scope

In scope:

  • Membership audience definition and export (name, phone, email)
  • Segmenting members by business unit and prior job type
  • Validating the membership count two independent ways

Out of scope for this SOP (see future revisions):

  • Drafting campaign copy
  • Podium send mechanics and opt-out handling
  • Call-code setup and response tracking

3. Source of truth

All membership data is read from the ServiceTitan production API, tenant 3306271893 (read-only scopes only). Two independent API surfaces return the numbers below, and both agree.

Contact points: SMS Email Podium Direct mail

4. How we derived the membership numbers

Two completely independent API pulls produced the same result. This is intentional: no single query is trusted until a second, structurally different one confirms it.

Headline numbers (verified 15 Sep 2026)
1,315 active member customers across 1,368 active memberships (some customers hold two membership rows). Gold 1,357 · Platinum 11. Total membership records in ServiceTitan: 2,615 (Active 1,368 · Expired 1,194 · Canceled 53).

Method A - Direct API pull (memberships/v2)

A1. Request a read token from auth.servicetitan.io (client-credentials, 15-minute expiry). Every call also carries the ST-App-Key header.
A2. Pull all memberships:
GET /memberships/v2/tenant/3306271893/memberships (loop page + hasMore; totalCount is often null)
A3. Pull membership types to label the tiers:
GET /memberships/v2/tenant/3306271893/membership-types
A4. Count by status: Active / Expired / Canceled. Result: Active = 1,368.

Note: the membership module slug is memberships/v2, not membership/v2 (the singular form returns 404).

Method B - Reporting API (Active Memberships report)

B1. List report categories, then reports within marketing:
GET /reporting/v2/tenant/3306271893/report-categories
GET /reporting/v2/tenant/3306271893/report-category/marketing/reports
B2. The Active Memberships report is id 2263. Pull its full data with a POST body of {"parameters": []}:
POST /reporting/v2/tenant/3306271893/report-category/marketing/reports/2263/data
B3. Rows come back with a header list (fields) and array rows. Count by MembershipStatus: Active = 1,368. Total rows = 2,615.
Reporting API rate limit
The Reporting API allows 1 run of the same report per minute per tenant. Large exports page through with ~65-second waits between pages. Plan big pulls accordingly.

5. Why we trust these numbers (two-way validation)

Method A (raw record API) and Method B (reporting API) are built on entirely different code paths, so an error in one would not be echoed by the other. They returned identical results on 15 Sep 2026:

Rule
A membership figure is only quoted as final after both methods agree. If they ever disagree, investigate the gap before any audience is sent or money is committed.

7. Learnings & pitfalls (append as discovered)

  • Membership slug is memberships/v2 - the singular membership/v2 returns 404. (2026-09-15)
  • Contacts are per-customer. The tenant-level contact list is forbidden (403); phones pull one customer at a time. The Active Memberships report avoids this bypass by returning phone/email inline. (2026-09-15)
  • First name is combined. ServiceTitan stores a single CustomerName (no native first/last split). Derive first name by splitting on the last space; label it derived in any export. (2026-09-15)
  • Reporting rate cap of 1/min per tenant per report. (2026-09-15)
