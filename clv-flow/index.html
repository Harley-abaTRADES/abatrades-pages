Members | New-Member Nurture

Split-automation build · one flow per trade · zero conditional splits
The service-type branch is handled by a contact filter on each automation's trigger, not a conditional-split block. So instead of one big flow with nested 2-way splits, you build 4 straight-line automations — one per trade. Each member is admitted to exactly ONE of them (the trade they bought), and the flow runs top-to-bottom. E1-Welcome goes to every member (no cohort filter); the treatment/control gate lives on the trade automations, so control members get the welcome but never the nurture flow.

Why split automations beat nested splits here: the earlier nested approach needed 9 conditional-split blocks (3 per email × E2/E3/E4). Splitting by trade moves that decision to a trigger contact filter — one filter per automation, zero split blocks. You build 4 identical straight lines instead of one branching tree.
Same limitation applies: a member must match one of the four SERVICE_TYPE values to be admitted. Anyone whose attribute is blank or unmatched would fall through all four filters and get nothing after E1. If that's possible, add a fifth "Other" automation with no SERVICE_TYPE filter to carry them — worth deciding as you wire it.
Source of truth: CLV membership deck. Templates built via API (ids 1–15). Cron 1 lane A fires member_joined; lane B fires member_invoice_paid on real invoice payment.
